Portable Reader staging acceptance — 30 September / 1 October 2026
======================================================

Agreed behavior
--------------
All 176 drive trajectories appear in the existing Reader selection interface.
Selecting Open reads the existing LGS, HDF, NPY and DFT files directly. The
portable viewer has no dataset-copy controls, copy API or cache fallback.
The optional compatibility setup copies application software only, after an
explanation and confirmation. Singularity and Apptainer each have an explicit launcher and read the
shared SIF image directly from the drive without that setup. A third launcher
selects the independent PRoot compatibility mode.

Scope and platform boundary
---------------------------
New Reader behavior is under Q_OS_LINUX, activated by
H5READER_LOCAL_LIBRARY_ROOT. Without that setting the existing HTTPS catalog
continues to operate. CMake includes the new source, catalog and tests only
on Linux. Windows Qt Pro logic and the HTTPS catalog are unchanged. A new
Windows binary was not built on this Linux host.

Catalog evidence
----------------
176 datasets: 173 MD trajectories and three small proteins.
24,553 frames and 7,253 DFT frame pairs.
The generator checked the supplied SSD inventories and staged LGS manifests,
including exact DFT rosters. It did not read the actual Provenance drive.
The catalog uses paths relative to the drive root and readable BMRB/protein
names; original identifiers and titles are retained.

Native validation
-----------------
33/33 CTest groups passed on the final direct-opening build, using CPU/software
rendering. This includes the legacy HTTPS selector, local selector, catalog,
REST, model input export/shutdown, CPU inference and small-protein DFT gates.
The main REST group reported 59 passed and 11 conditional skips; fixture-
specific ML, export and small-protein cases run in separate configured gates.
The catalog generator's 14 tests passed. An independent code review confirmed
that local opening cannot substitute a previous cache or start a download.

Portable validation
-------------------
Apptainer 1.5.3, Ubuntu 24.04 host; image carries Ubuntu 24.04.4 userspace.
Final SIF launched the actual Reader with its source mount read-only.
REST and snapshots verified all 176 entries, direct BMRB 7057 opening,
100 frames with navigation to frame 99, and zero dataset copies.
No local application runtime was extracted on the Apptainer route.
Desktop activation through Gio.DesktopAppInfo launched the actual Reader and
selector from a drive path containing spaces, with automatic drive discovery.
26,878 staged scientific files were unchanged by SHA-256 before/after.
CPU model atom-16 result: 29.76103401184082.
Rendering: llvmpipe (LLVM 20.1.2). No GPU computation was requested.
The optional fallback setup GUI was tested for cancellation before setup and
during extraction. Both exited with no extracted runtime or worker leftovers.

Older Linux compatibility validation
------------------------------------
AlmaLinux 8.10: actual kernel 4.18.0-553.16.1, host glibc 2.28,
SingularityCE 3.8.4 (released October 2021), Haswell CPU feature mask.
Full Reader acceptance passed: Qt/VTK rendering, CPU inference with the same
29.76103401184082 reference result, all 176 selector entries, opening BMRB 7057,
100 frames and navigation to frame 99, source read-only, hashes unchanged,
no trajectory copies and no local application extraction. This used an actual
KVM guest kernel, not an older userspace container on a newer host kernel.

CentOS 7.9: actual kernel 3.10.0-1160.80.1, host glibc 2.17,
SingularityCE 3.8.4, SELinux Enforcing, user namespaces disabled, Haswell CPU.
The same full acceptance passed, including CPU prediction, all 176 entries,
100-frame BMRB navigation to frame 99 and unchanged source hashes. The test VM
needed its normal Mesa DRI packages for the Xvfb software OpenGL display.
No Reader or image change was needed. The engine used its installed setuid
helper, as on sites that provide Singularity without unprivileged namespaces.

The same final package also passed fresh explicit Apptainer and PRoot runs on
the development host. Both verified CPU inference, rendering, all 176 entries,
direct trajectory navigation and 26,878 scientific fixture files unchanged.
PRoot extracted application software only into its fresh local workspace.

Carried Apptainer 1.5.3 (EL8 package) also passed the complete Reader acceptance
on the AlmaLinux 8 VM: CPU inference, rendering, all 176 entries, frame 99,
source read-only, source hashes unchanged, and no trajectory copies or Reader
image extraction. A separate real Qt startup passed with the drive, package
and SIF under a path containing spaces and the engine in local application
storage. The carried engine needs glibc 2.28+, permitted user namespaces and
executable local storage. The one-time 163 MB engine setup explanation was
exercised with both approval and cancellation; cancellation copied zero engine
files, approval produced a working engine, later checks reused it, and no
partial setup directories remained. Workspace paths containing whitespace are
rejected for this engine before copying. Concurrent setup calls returned one
completed cache, and symlink cache entries were rejected without writes outside
the workspace. The integrated packaged launcher then prepared and used that
cache on AlmaLinux 8 through a spaced drive path; both actual Reader Qt startup
and the packaged compatibility checker passed. PRoot remains a separate option.

Memory observation: the initial 4 GiB VM rendered successfully but the optional
CPU model could not allocate a roughly 4 GB tensor. Full inference passed with
a 12 GiB VM. This is an observed fixture requirement, not a universal minimum;
model memory depends on the selected protein. Basic viewing is separate.

Explicit engine shortcuts, the automatic launcher, fallback setup explanation,
and a local compatibility-report shortcut accompany the package. The checker
uses synthetic data only, tests source read-only binding and Qt/X11 startup,
and reports runtime/version, display and policy failures without unpacking the
fallback or accessing trajectory files. Scripts support the older Singularity
CLI; they do not assume recent Apptainer-only options.
